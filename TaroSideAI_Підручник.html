Розділ 1. Що таке TaroSideAI

1.1 Що робить застосунок

Розділ 2. Чиста архітектура (Clean Architecture)

Твій бекенд поділений на 4 проєкти: Domain, Application, Infrastructure, API. Це і є Clean Architecture. Ти цю тему вже розумів непогано — тут закріпимо й додамо точності.

2.1 Чотири шари

Рис. 2. Що ближче до центру — то «чистіше» й незалежніше. Domain не знає ні про кого. API знає всіх.

2.2 Правило залежностей

Головне правило Clean Architecture: залежності спрямовані тільки всередину. Зовнішній шар може посилатися на внутрішній, але ніколи навпаки. У твоєму .csproj це видно буквально:

// TaroSideAI.Application.csproj — Application бачить тільки Domain
<ProjectReference Include="..\TaroSideAI.Domain\TaroSideAI.Domain.csproj" />

// TaroSideAI.Infrastructure.csproj — Infrastructure бачить Application
<ProjectReference Include="..\TaroSideAI.Application\..." />

// TaroSideAI.API.csproj — API бачить і Infrastructure, і Application
<ProjectReference Include="..\TaroSideAI.Infrastructure\..." />
<ProjectReference Include="..\TaroSideAI.Application\..." />
🔬 Глибше: як Domain «командує» Infrastructure, не знаючи про неї Виникає парадокс: бізнес-логіка (Application) хоче дістати карти з бази, але база — це Infrastructure, на яку Application НЕ має права посилатися. Як же бути?

Відповідь — інверсія залежностей (буква D у SOLID). Application оголошує інтерфейс ICardRepository («мені потрібен хтось, хто вміє діставати карти»), а Infrastructure його реалізує (CardRepository). Тепер стрілка залежності «перевернута»: Infrastructure залежить від Application, а не навпаки. Саме тому твої інтерфейси лежать в Application/Interfaces, а їхні реалізації — в Infrastructure/Repositories.

2.3 Навіщо так складно

Ти у відповіді на питання сказав «для безпеки». Це частково так, але головні причини інші:

ПричинаЩо це дає на практиці
ТестопридатністьМожна підмінити ICardRepository фейковою заглушкою і тестувати CardService без реальної бази
ЗамінністьЗахочеш замінити PostgreSQL на MongoDB — переписуєш тільки Infrastructure, логіка не чіпається
Чистота логікиБізнес-правила не змішані з SQL і HTTP — їх легко читати й змінювати
Незалежність командОдин розробник пише логіку, інший — доступ до даних, не заважаючи один одному
🎤 На співбесіді спитають: «Що таке Clean Architecture і навіщо вона?» «Це поділ застосунку на шари за принципом залежностей, спрямованих усередину. Внутрішні шари (Domain з сутностями) нічого не знають про зовнішні. Зовнішні (API, доступ до БД) залежать від внутрішніх. Це досягається через інтерфейси: Application оголошує контракт, Infrastructure його реалізує. Головна вигода — логіку можна тестувати й змінювати незалежно від бази даних чи фреймворку. У моєму проекті це 4 проєкти: Domain, Application, Infrastructure, API.»

Розділ 3. Domain — серце системи

Domain — це найвнутрішніший шар. Тут лежать сутності (Entities) — звичайні C#-класи, що описують об'єкти твоєї предметної області, та enum-и. Жодного EF Core, жодного HTTP — чистий C#.

3.1 Карта сутностей (ERD)

Спершу подивись, як твої сутності пов'язані між собою. Стрілка «1 — ∞» означає «один до багатьох»: у одного користувача багато розкладів тощо.

Рис. 3. ERD-діаграма: ReadingCard — це зв'язкова (pivot) таблиця між Reading і TarotCard, бо один розклад містить багато карт, а одна карта може з'являтися в багатьох розкладах (зв'язок «багато-до-багатьох»).

3.2 Розбір ключових сутностей

AppUser — користувач

public class AppUser : IdentityUser<Guid>
{
    public UserRole Role { get; set; } = UserRole.Free;
    public int DailyQuestionsUsed { get; set; } = 0;
    public DateOnly DailyQuestionsReset { get; set; } = ...;
    public ICollection<Reading> Readings { get; set; } = [];
}

Ти успадкував IdentityUser<Guid> — і безкоштовно отримав Email, PasswordHash, UserName, SecurityStamp від ASP.NET Identity. Зверху додав своє: роль, лічильники денних лімітів. Readings — це навігаційна властивість: EF Core розуміє, що в користувача є колекція розкладів.

🔬 Глибше: чому Guid замість int для Id? У коментарі ти написав «Guid краще за int для безпеки». Точніше: послідовні int-ідентифікатори (1, 2, 3…) можна вгадати — зловмисник бачить /users/5 і пробує /users/6. Guid (наприклад a3f1...c9) вгадати неможливо. Мінус — Guid більший і повільніший як індекс. Тому картки й розклади в тебе мають int Id (вони не секретні), а користувачі й чати — Guid (їх не можна перебирати). Це продумане рішення.

TarotCard, Spread, Reading, ReadingCard

СутністьПризначенняЦікаве поле

SpreadТип розкладу (3/5/7/12 карт)RequiredRole — мінімальна роль для доступу; IsFreeMode — користувач сам обирає кількість

3.3 Enum-и та політики ролей

У тебе три enum-и: Arcana (Major/Minor), Suit (Wands/Cups/Swords/Pentacles) і UserRole (Guest/Free/Premium/Vip/Admin). А найцікавіше — RolePolicy: це record, що описує, що дозволено кожній ролі.

public static RolePolicy For(UserRole role) => role switch
{
    UserRole.Free => new RolePolicy {
        MaxReadingsPerDay = 2, MaxChatMessagesPerDay = 20, MaxCards = 3 ... },
    UserRole.Premium => new RolePolicy {
        MaxReadingsPerDay = 7, PdfExport = true, BetterAiPrompt = true ... },
    ...
};

Це дуже зручний патерн: вся «матриця можливостей» зібрана в одному місці. Коли підключатимеш оплату (Розділ 11), тобі лишиться тільки міняти user.Role — і всі ліміти зміняться автоматично.

🎤 На співбесіді: «Що таке navigation property в EF Core?» «Це властивість сутності, що посилається на пов'язану сутність або колекцію. Наприклад, AppUser.Readings — колекція розкладів користувача. EF Core за нею розуміє зв'язки між таблицями й може підвантажувати пов'язані дані через Include().»

Розділ 4. Infrastructure — робота з базою (EF Core)

Infrastructure — це шар, де абстракції стають реальністю. Тут живе AppDbContext, репозиторії, конфігурації таблиць і міграції. Тільки тут дозволено використовувати Entity Framework Core.

4.1 Що таке ORM і EF Core

📌 Простими словами ORM (Object-Relational Mapping) — це перекладач між світом C#-об'єктів і світом таблиць SQL. Замість того щоб писати SELECT * FROM TarotCards, ти пишеш _db.TarotCards.ToListAsync(), а EF Core сам генерує SQL, виконує його і перетворює рядки таблиці на C#-об'єкти TarotCard.

4.2 AppDbContext — головний вхід до бази

public class AppDbContext : IdentityDbContext<AppUser, IdentityRole<Guid>, Guid>
{
    public DbSet<TarotCard> TarotCards => Set<TarotCard>();
    public DbSet<Spread> Spreads => Set<Spread>();
    public DbSet<Conversation> Conversations => Set<Conversation>();
    // ... ще Readings, ReadingCards, Messages

    protected override void OnModelCreating(ModelBuilder builder)
    {
        base.OnModelCreating(builder); // Identity налаштовує свої таблиці
        builder.ApplyConfigurationsFromAssembly(typeof(AppDbContext).Assembly);
    }
}

Кожен DbSet<T> — це, по суті, таблиця в базі. DbSet<TarotCard> ⇄ таблиця TarotCards. Оскільки ти успадкував IdentityDbContext, EF Core автоматично додав ще й таблиці Identity: AspNetUsers, AspNetRoles тощо.

Рядок ApplyConfigurationsFromAssembly каже: «знайди всі класи, що реалізують IEntityTypeConfiguration<T>, і застосуй їх». Саме так підключаються твої seed-дані.

4.3 Конфігурації та seed (засів даних)

У TarotCardConfiguration ти через HasData() «засіваєш» усі 78 карт прямо в міграцію. Тобто колода народжується разом із базою.

public class TarotCardConfiguration : IEntityTypeConfiguration<TarotCard>
{
    public void Configure(EntityTypeBuilder<TarotCard> builder)
    {
        builder.HasData(
            new TarotCard { Id = 1, NameUkr = "Дурень", Arcana = Arcana.Major, ... },
            // ... ще 77 карт
        );
    }
}
📌 Чому це розумно Раніше карти жили на фронтенді (tarotData.ts). Ти переніс їх у бекенд — і тепер база даних стала «єдиним джерелом правди». Фронт і AI беруть однакові дані. Це правильний інженерний крок.

4.4 Репозиторії — реалізація контрактів

Пам'ятаєш інтерфейс ICardRepository з Application? Ось його реалізація в Infrastructure:

public class CardRepository : ICardRepository
{
    private readonly AppDbContext _db;
    public CardRepository(AppDbContext db) => _db = db;

    public async Task<TarotCard> CreateAsync(TarotCard card)
    {
        _db.TarotCards.Add(card);
        await _db.SaveChangesAsync(); // тут летить INSERT у БД
        return card; // після Save — card.Id вже заповнений базою
    }
    public async Task<List<TarotCard>> GetAllAsync() => await _db.TarotCards.ToListAsync();
}

МетодЩо робитьДе в тебе

.FindAsync(id)Шукає за первинним ключемGetByIdAsync

🔬 Глибше: що таке міграція Ти у відповіді сказав влучно: «міграція — це історія БД + перетворений C#-код у SQL». Точніше: міграція — це згенерований EF Core клас, що описує, як змінити схему бази, щоб вона відповідала твоїм сутностям. У тебе дві міграції: InitialCreate (створення таблиць) і SeedCardsAndSpreads (засів карт і розкладів).

Цикл роботи: 1) міняєш сутність у C# → 2) dotnet ef migrations add Назва (EF порівнює модель зі знімком і генерує різницю) → 3) dotnet ef database update (застосовує SQL до бази). Якщо змінити сутність і не зробити міграцію — у БД не буде нової колонки, і при запиті EF кине помилку, бо модель і реальна схема розійшлися.
⚠️ Що покращити: проблема N+1 і tracking FindAsync і ToListAsync за замовчуванням відстежують (tracking) об'єкти — EF тримає їх у пам'яті, щоб помітити зміни. Для запитів «тільки прочитати» це зайве навантаження — там варто додавати .AsNoTracking().

Також стережись N+1: якщо в циклі звертатися до conversation.Messages без Include, EF зробить окремий запит на кожен елемент. Ти правильно використав .Include(c => c.Messages) у ConversationRepository — це і є захист від N+1.
🎤 На співбесіді: «Lazy vs Eager loading?» «Eager loading — пов'язані дані завантажуються одразу через Include() одним запитом з JOIN. Lazy loading — підвантажуються автоматично при першому зверненні до навігаційної властивості, що може спричинити проблему N+1. У моєму проекті я використовую eager loading через Include для повідомлень чату.»

5.2 Приклад: витягування карт

Серце ігрової механіки — CardService.DrawRandomCardsAsync. Подивись, як акуратно тут усе зроблено:

public async Task<List<ReadingCard>> DrawRandomCardsAsync(int count)
{
    if (count <= 0)
        throw new ArgumentException("Кількість карт має бути більше 0");

    var allCards = await _cardRepository.GetAllAsync();       // 1. вся колода
    if (count > allCards.Count) throw new InvalidOperationException(...);

    var random = Random.Shared;
    var drawn = allCards.OrderBy(_ => random.Next()).Take(count).ToList(); // 2. перемішати

    var result = new List<ReadingCard>();           // 3. позиція + перевернутість
    for (int i = 0; i < drawn.Count; i++)
        result.Add(new ReadingCard {
            Card = drawn[i], Position = i + 1,
            IsReversed = random.Next(2) == 1   // 50% шанс перевернутої
        });
    return result;
}

Три чіткі кроки: дістати колоду → перемішати й узяти потрібну кількість → присвоїти позицію і випадкову «перевернутість». Захист від помилкового вводу на початку — гарна звичка.

5.3 DTO — навіщо вони

📌 Простими словами DTO (Data Transfer Object) — це «спрощена коробка» для передачі даних між шарами або клієнту. Вона містить тільки потрібні поля й нічого зайвого.

Приклад: AuthResponseDto повертає клієнту лише Token, UserName, Role — але НЕ PasswordHash. Якби ти повертав сутність AppUser напряму, ризикував би злити в JSON хеш пароля чи службові поля Identity.

public class AuthResponseDto
{
    public string Token { get; set; } = "";
    public string UserName { get; set; } = "";
    public string Role { get; set; } = "";
}

У SpreadService ти явно перетворюєш сутність на DTO методом MapToDto — це і є межа, через яку «сирі» сутності не виходять назовні.

🔬 Глибше: Entity vs DTO — три причини розділяти 1. Безпека: не світимо службові/секретні поля. 2. Стабільність API: можна змінити сутність у базі, не ламаючи формат, який очікує фронт. 3. Форма під клієнта: DTO може об'єднувати дані з кількох сутностей (як ReadingResponseDto, що містить і дані розкладу, і список карт).

5.4 Options — типізовані налаштування

JwtSettings і AiSettings — це класи, у які підвантажуються секції з appsettings.json. Замість того щоб всюди тягати «магічні рядки» з конфігу, ти отримуєш строго типізований об'єкт через IOptions<JwtSettings> (побачимо в Розділі 8).

⚠️ Що покращити в цьому шарі 1. Сервіси (CardService, AuthService тощо) не мають інтерфейсів — лише репозиторії мають. Для тестопридатності варто завести ICardService і т.д. 2. Скрізь throw new Exception("...") — краще власні типи винятків (NotFoundException, ValidationException). Це зробить обробку помилок керованою (див. Розділ 6). 3. Підключений FluentValidation, але валідатори варто перевірити — чи реально вони відсікають порожні логіни/паролі.

Розділ 6. API — контролери й ендпоінти

Розділ 7. Program.cs — як усе збирається докупи

Program.cs — це «точка збірки» (composition root). Тут реєструються всі залежності, налаштовується конвеєр обробки запиту й запускається застосунок. Це тема, де в тебе були прогалини — розберемо ретельно.

7.1 Dependency Injection (DI) — реєстрація

Ти у відповіді добре пояснив суть DI: «просиш інтерфейс — контейнер сам будує ланцюжок об'єктів». Саме так. У Program.cs ти кажеш контейнеру, яку реалізацію давати:

builder.Services.AddScoped<ICardRepository, CardRepository>();
builder.Services.AddScoped<CardService>();
builder.Services.AddScoped<AuthService>();
builder.Services.AddSingleton<IChatClient>(...);  // клієнт до Ollama

Коли CardService просить у конструкторі ICardRepository, контейнер бачить реєстрацію й автоматично створює CardRepository, який, своєю чергою, отримує AppDbContext. Ти ніде не пишеш new CardRepository() — це і є інверсія керування (IoC).

📌 Простими словами Уяви ресторан. Ти (сервіс) кажеш офіціанту «принеси інгредієнти» (просиш інтерфейс), і тобі їх приносять. Тобі байдуже, з якого складу їх узяли. DI-контейнер — це той офіціант + склад.

7.2 Три «строки життя» (lifetimes) — ВАЖЛИВО

Це питання тобі провалив на самоперевірці, і це топ-питання співбесід. Запам'ятай таблицю:

LifetimeСкільки живе екземплярКоли вживатиУ твоєму коді
AddScopedОдин на один HTTP-запитСервіси й репозиторії, що працюють з БДусі сервіси та репозиторії
AddSingletonОдин на весь час життя застосункуВажкі/незмінні об'єкти без стану запитуIChatClient (клієнт Ollama)

Рис. 5. Три lifetime DI-контейнера наочно.
⚠️ Тонкість, яку люблять на співбесідах Не можна впроваджувати Scoped у Singleton. Singleton живе вічно, а Scoped — один запит; якщо Singleton «схопить» Scoped, той «застрягне» назавжди (captive dependency). Тому AppDbContext (Scoped) ніколи не можна тримати в Singleton-сервісі.

7.3 Конвеєр middleware — порядок вирішує все

Ти сказав, що middleware — «проміжна штука». Точніше: middleware — це ланка в конвеєрі обробки запиту. Кожен запит проходить ланки по черзі, і порядок критичний.

var app = builder.Build();
if (app.Environment.IsDevelopment()) { app.UseSwagger(); app.UseSwaggerUI(); }
app.UseHttpsRedirection();
app.UseCors("FrontendPolicy");
app.UseAuthentication();  // ХТО ти?
app.UseAuthorization();   // що тобі МОЖНА?
app.MapControllers();
Рис. 6. Конвеєр middleware. Перевернеш порядок Authentication/Authorization — і перевірка прав не знатиме, хто користувач.
🎤 На співбесіді: «У чому різниця між Authentication і Authorization?» «Authentication (автентифікація) — встановлення особи: хто ти? У моєму проекті це перевірка JWT-токена. Authorization (авторизація) — перевірка прав: що тобі дозволено? Це атрибут [Authorize] на контролерах. Спершу йде автентифікація, потім авторизація — тому в pipeline UseAuthentication() стоїть перед UseAuthorization().»

Розділ 8. Автентифікація і JWT (детально)

Це була твоя головна прогалина. Ти думав, що сервер зберігає токен — насправді ні. У цьому весь сенс JWT. Розберемо повільно й до кінця.

8.1 Що таке JWT і головна ідея

🔬 Ключова ідея: JWT — stateless (без стану) Сервер НЕ зберігає виданий токен ніде. Токен сам по собі — самодостатній «паспорт»: у ньому записано, хто ти, і він підписаний секретним ключем сервера. При кожному запиті сервер просто перевіряє підпис математично — і якщо підпис валідний і термін не вийшов, довіряє вмісту. Жодного звернення до бази, жодної таблиці сесій.

Порівняй із класичними сесіями: там сервер тримає в пам'яті/базі таблицю «сесія → користувач». JWT цього не потребує — тому легко масштабується на багато серверів.

8.2 Анатомія токена

JWT складається з трьох частин через крапку: header.payload.signature

Рис. 7. Будова JWT. Підпис гарантує цілісність: змінити роль у payload не можна, бо підпис перестане сходитись.

8.3 Як ти генеруєш токен — TokenService

public string GenerateToken(AppUser user)
{
    var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(_jwt.SecretKey));
    var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

    var claims = new List<Claim> {
        new(JwtRegisteredClaimNames.Sub, user.Id.ToString()),   // хто
        new(JwtRegisteredClaimNames.UniqueName, user.UserName),
        new(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString()) // унікальний id токена
    };
    claims.Add(new Claim(ClaimTypes.Role, user.Role.ToString()));  // роль

    var token = new JwtSecurityToken(
        issuer: _jwt.Issuer, audience: _jwt.Audience, claims: claims,
        expires: DateTime.UtcNow.AddMinutes(_jwt.ExpiresInMinutes),
        signingCredentials: creds);
    return new JwtSecurityTokenHandler().WriteToken(token);
}

Claim — це «твердження» про користувача («id = ...», «роль = Premium»). Ти кладеш їх у токен, підписуєш секретним ключем і віддаєш клієнту. Jti (унікальний id токена) і exp (термін) додаються для безпеки. Ось чому «токен щоразу інший», як ти й помітив — через час видачі та Jti.

8.4 Повний цикл: вхід і захищений запит

Рис. 8. Зверни увагу: при захищеному запиті сервер НЕ ходить у базу по токен. Він лише перевіряє підпис ключем. Це і є stateless.

8.5 Налаштування перевірки в Program.cs

.AddJwtBearer(options => {
    options.TokenValidationParameters = new TokenValidationParameters {
        ValidateIssuer = true, ValidateAudience = true,
        ValidateLifetime = true,            // термін дії
        ValidateIssuerSigningKey = true,    // головне: перевірка підпису
        IssuerSigningKey = new SymmetricSecurityKey(...SecretKey)
    };
});

Той самий SecretKey використовується і для підпису (видача), і для перевірки. Тому він має бути таємним: хто знає ключ — може підробити будь-який токен.

⚠️ Що покращити 1. AuthService кидає throw new Exception("Invalid username or password") — однакове повідомлення (це ти зробив правильно для безпеки!), але тип винятку загальний; краще власний UnauthorizedException. 2. Токен живе в localStorage на фронті — це зручно, але вразливо до XSS. Альтернатива — httpOnly cookie. Для навчального проекту localStorage прийнятно, але знай про компроміс. 3. Немає refresh-токенів — коли access-токен спливає (60 хв), користувача викидає. У api.ts ти лишив коментар, що це місце для майбутньої refresh-логіки.
🎤 На співбесіді: «Чому JWT називають stateless і де він зберігається?» «JWT stateless, бо сервер не зберігає токен — уся потрібна інформація (id, роль, термін) лежить усередині самого токена й захищена підписом. Сервер при кожному запиті лише перевіряє підпис своїм секретним ключем, без звернення до бази. Зберігається токен на клієнті — у моєму випадку в localStorage браузера — і надсилається в заголовку Authorization: Bearer.»

Розділ 9. AI та function calling (детально)

Це твоя фішка — і саме її варто розуміти ідеально, бо вона виділяє тебе серед інших джунів. Тут ти мав найбільшу хибну уяву: думав, що сам розбираєш відповідь рядком (if result == "drawtarotcards"). Насправді все інакше — і краще.

9.1 Розвінчуємо головну хибну уяву

⚠️ Як ти думав (наївна схема) «Модель повертає текст. Я роблю result.ToLower(), перевіряю if == "drawtarotcards", і якщо так — викликаю функцію.» Такого коду в тебе НЕМАЄ. Ручного розбору рядків ніде немає.
🔬 Як насправді (structured function calling) Бібліотека Microsoft.Extensions.AI робить це за тебе. Ти реєструєш функцію як «інструмент», а модель повертає не текст «drawtarotcards», а структурований запит на виклик інструмента (з ім'ям функції й аргументами). Фреймворк сам розпізнає цей запит, сам викликає твою C#-функцію, сам віддає результат назад моделі — і все це в один автоматичний цикл завдяки .UseFunctionInvocation().

9.2 Налаштування клієнта (Program.cs)

builder.Services.AddSingleton<IChatClient>(sp => {
    var cfg = ...GetSection("Ollama").Get<AiSettings>();
    IChatClient ollama = new OllamaApiClient(new Uri(cfg.OpenAiApiUrl), cfg.OpenAiModel);
    return new ChatClientBuilder(ollama)
        .UseFunctionInvocation()   // ← вмикає авто-виклик інструментів!
        .Build();
});

Цей рядок .UseFunctionInvocation() — і є вся «магія». Він обгортає клієнт логікою, що автоматично виконує цикл «модель попросила інструмент → виклич його → поверни результат → дай моделі продовжити».

9.3 Реєстрація інструмента (ChatAiService)

var drawCardsTool = AIFunctionFactory.Create(
    DrawTarotCardsAsync,                // твій C#-метод
    name: "DrawTarotCards",
    description: "Витягує карти Таро. ОБОВ'ЯЗКОВО викликай, коли просять ворожіння.");

var options = new ChatOptions {
    Tools = [drawCardsTool],
    ToolMode = ChatToolMode.Auto    // модель САМА вирішує, чи кликати
};

Ось відповідь на питання «хто вирішує, коли викликати функцію»: модель, на основі description інструмента й тексту користувача. Ти лише даєш їй інструмент і кажеш «вирішуй сама» (ToolMode.Auto).

9.4 Повний цикл одного ворожіння

Рис. 9. Цикл function calling. Червона стрілка — структурований запит на інструмент (не звичайний текст!).

9.5 System prompt і guardrails

Ти задаєш моделі роль через системний промпт: персонаж «Lunaris», тон, і — найважливіше для інженера — обмеження (guardrails):

9.6 Чому карти тягне код, а не модель

🔬 Найважливіша архітектурна ідея проекту LLM схильна до галюцинацій — вона б «вигадала» карти, які звучать правдоподібно, але не з твоєї колоди, без справжньої випадковості й без гарантії, що така карта взагалі існує. Тому ти зробив правильно: випадковість і факти — на боці коду (DrawRandomCardsAsync + база), а модель отримує вже готові реальні карти й лише інтерпретує їх. У функції ти явно повертаєш моделі тільки факти: 
return $"Витягнуті карти:\n{карти}\n\nТвоя задача: інтерпретуй ці карти...";
Це патерн «LLM як інтерпретатор, а не джерело правди» — саме так будують надійні AI-фічі в продакшені.

9.7 Як це під'єднано до чату

ConversationService.ProcessUserMessageAsync зв'язує все: зберігає повідомлення користувача, бере останні 10 повідомлень як історію, кличе ChatAiService.ChatAsync, зберігає відповідь AI. Обмеження історії до 10 повідомлень — розумно: це економить контекст моделі й швидкість.

🎤 На співбесіді: «Розкажи про найскладнішу частину свого проекту» «Інтеграція LLM через function calling. Я реєструю C#-метод як інструмент через AIFunctionFactory, а модель у режимі ToolMode.Auto сама вирішує, коли його викликати. Бібліотека Microsoft.Extensions.AI з UseFunctionInvocation автоматично виконує виклик і повертає результат моделі. Карти тягне мій код із бази, а не модель — щоб уникнути галюцинацій. Модель отримує реальні факти й лише інтерпретує їх. Плюс я задав guardrails у системному промпті проти медичних/фінансових порад.»

10.2 api.ts — єдина точка зв'язку з бекендом

Ти зробив акуратний обгортач навколо fetch. Уся комунікація з API проходить через нього — і саме тут автоматично додається JWT:

export async function api<T>(path, init = {}): Promise<T> {
  const token = auth.getToken();
  const headers = new Headers(init.headers);
  headers.set('Content-Type', 'application/json');
  if (token) headers.set('Authorization', `Bearer ${token}`); // ← JWT тут

  const res = await fetch(`${API_URL}${path}`, { ...init, headers });
  if (!res.ok) { /* дістаємо message сервера й кидаємо Error */ }
  return res.json();
}

Об'єкт auth керує токеном і профілем у localStorage (ключі lunaris_jwt, lunaris_user). Це і є та клієнтська «пам'ять», де живе твій токен.

10.3 Як фронт і бек зустрічаються — приклад логіну

Сторінка Login.tsx показує повний танець фронт↔бек:

const data = await api('/api/auth/login', {              // 1. шлемо логін/пароль
  method: 'POST', body: JSON.stringify(form) });
auth.setToken(data.token);                              // 2. зберігаємо токен
const user = await api('/api/user/me');                  // 3. тягнемо профіль (з токеном)
auth.setUser(user);
navigate('/profile');                                    // 4. переходимо в профіль

Зверни увагу на крок 3: запит до /api/user/me вже піде з заголовком Authorization: Bearer ..., бо api() автоматично підставив щойно збережений токен. Так замикається весь ланцюг автентифікації з Розділу 8.

📌 Що таке SPA і CORS SPA — застосунок, де сторінка не перезавантажується; React сам перемальовує вміст, а дані тягне через API. Оскільки фронт (localhost:5173) і бек (localhost:5080) — різні адреси, браузер за замовчуванням блокує запити між ними. Саме тому в Program.cs ти налаштував CORS-політику FrontendPolicy, що дозволяє запити з адреси фронту.

⚠️ Що покращити 1. Немає захищених роутів: будь-хто може відкрити /profile без токена (сторінка просто впаде на запиті). Варто додати компонент ProtectedRoute, що редіректить неавторизованих на /login. 2. Немає глобальної обробки 401 — коли токен спливає, добре б автоматично розлогінювати. У коментарі api.ts ти це передбачив на майбутнє.

11.4 Потік підписки крок за кроком

Рис. 11. Потік оплати підписки. Рожева стрілка (webhook) — єдине надійне джерело правди про оплату.

11.5 Критичні правила безпеки

⚠️ Три помилки, які роблять новачки (не повтори їх) 1. Не вір редіректу. Користувач повертається на твій сайт через redirect — але це НЕ доказ оплати (його можна підробити, ввівши URL вручну). Роль підвищуй тільки з webhook від PSP.
2. Завжди перевіряй підпис webhook. PSP підписує повідомлення твоїм секретним ключем (як JWT!). Якщо підпис не сходиться — це фальшивка, ігноруй. Інакше будь-хто надішле тобі «оплата успішна» і отримає Premium безкоштовно.
3. Ідемпотентність. PSP може надіслати webhook двічі. Перевіряй ProviderOrderId: якщо платіж уже оброблено — не обробляй удруге (інакше подвоїш підписку).

Приклад обробки webhook (Application)

public async Task HandleWebhookAsync(PaymentCallback cb)
{
    if (!_provider.VerifySignature(cb))           // 1. перевірка підпису
        throw new UnauthorizedException("Bad signature");

    var payment = await _repo.GetByOrderIdAsync(cb.OrderId);
    if (payment is null || payment.Status == PaymentStatus.Success)
        return;                                   // 2. ідемпотентність

    if (cb.IsSuccess) {
        payment.Status = PaymentStatus.Success;
        var user = await _userManager.FindByIdAsync(payment.UserId.ToString());
        user.Role = payment.TargetRole;          // 3. підвищуємо роль!
        await _userManager.UpdateAsync(user);
    }
    await _repo.SaveAsync(payment);
}

11.6 Регулярні платежі (підписка щомісяця)

Для справжньої підписки PSP при першій оплаті повертає токен картки (recurring token). Ти зберігаєш його (НЕ саму картку!) і раз на місяць ініціюєш платіж цим токеном. Якщо платіж не пройшов — понижуєш роль назад до Free. Зручно винести це в фонову задачу (BackgroundService / Hangfire), що раз на добу перевіряє, кому час продовжувати.
